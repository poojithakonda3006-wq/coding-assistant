## 3. PROJECT OBJECTIVE

Build a working application that helps users identify programming errors, understand their causes, investigate them through progressive hints, obtain corrected code, and validate proposed fixes.

The product must combine deterministic software-analysis tools with AI-assisted reasoning.

The central workflow is:

**Submit Code → Detect Errors → Explain Findings → Provide Hints → Guide Debugging → Propose a Fix → Validate the Fix → Explain the Result**

The application must prioritize understanding and learning rather than simply generating replacement code.

A user should be able to submit a faulty Python program, understand the problem, attempt a correction with hints, request a proposed repair, review the code changes, and inspect the actual verification results.

The system must distinguish between:

* A confirmed diagnostic from a deterministic tool.

* An AI-generated hypothesis about a defect.

* A proposed correction that has not been executed.

* A correction that passed specific checks.

* A problem that remains unresolved.

Never represent an AI-generated hypothesis as a proven fact.

## 4. BUSINESS CONTEXT

### 4.1 Problem statement

Beginner programmers frequently encounter syntax errors, undefined variables, type errors, runtime exceptions, and logical defects.

Existing tools can provide error messages, static diagnostics, AI explanations, code suggestions, and automated repairs. However, a learner may still struggle to understand why the problem occurred, which code caused it, what to try first, and whether a proposed correction actually works.

This project addresses that educational and usability challenge by combining analysis, explanations, progressive hints, guided debugging, correction proposals, and evidence-backed validation.

### 4.2 Product differentiation

Do not claim that the product is the first AI coding assistant or that competitors lack individual features.

The intended differentiator is the integration of:

1. Multi-level error detection.

2. Beginner-friendly explanations.

3. Progressive hints that can delay full solutions.

4. Explicit repair limitations and verification status.

5. Reviewable corrected code.

6. Evidence-informed diagnosis.

7. Step-by-step debugging guidance.

Potential competitors and technical references include GitHub Copilot, Replit AI, Cline, Continue, CodeQL, Pylint, Ruff, and academic work on automated program repair.

Treat these as architectural and product references, not as exhaustive competitive research or verified feature-by-feature evaluations.

Do not scrape proprietary systems, copy proprietary designs, or make unsupported superiority claims.

### 4.3 Product success criteria

The project should demonstrate that:

* Users can submit code and receive structured diagnostics.

* The application can explain supported error categories in understandable language.

* Hint mode can withhold the full solution until the user requests it.

* The system can propose corrections without automatically overwriting the original code.

* Corrections can be checked using actual analysis tools and permitted tests.

* The interface communicates unresolved issues and verification limitations.

* Critical workflows work end to end.

* The project can be installed and run using documented instructions.

Do not invent numerical success metrics. Establish baselines through testing and report measured outcomes.

## 9. REQUIREMENTS

Classify implementation work by priority.

### P0 — Critical functional requirements

#### FR-01: Code submission

Users must be able to submit code through a usable editor or input interface.

Capture the selected programming language and any optional context such as:

* Error message or traceback.

* Expected output.

* Actual output.

* Sample input.

* Relevant test cases.

Validate input size and reject unsupported or malformed requests.

#### FR-02: Multi-level error detection

For Python, implement the supported stages:

1. Syntax and parsing diagnostics.

2. Static analysis.

3. Runtime exceptions.

4. Logical defects evaluated against expected behavior or tests.

5. Optional code-quality and security findings where feasible.

Do not claim that every stage can detect every bug.

#### FR-03: Structured diagnostic report

Each finding should contain, where applicable:

* Stable finding identifier.

* Error category.

* Severity.

* Message.

* Source location.

* Relevant code excerpt.

* Detection source.

* Evidence or explanation.

* Confidence description.

* Recommended next action.

Use nullable fields when information is unavailable. Never fabricate line numbers or evidence.

#### FR-04: Error explanations

Explain:

* What happened.

* Why it may have happened.

* Where the problem is located.

* What programming concept is involved.

* What the user can investigate next.

Distinguish confirmed tool output from AI interpretation.

#### FR-05: Progressive hints

Implement beginner learning mode with progressive hint levels:

* Level 1: Conceptual clue.

* Level 2: Relevant location or operation.

* Level 3: More specific corrective direction.

* Full solution: Explicitly requested correction.

Allow users to reveal hints progressively.

Do not include the complete corrected code in an earlier hint response.

Implement the hint-disclosure rule in the Python backend, not solely through hidden frontend controls or prompt instructions.

#### FR-06: Guided debugging

Provide a sequence that may include:

1. Reproduce or inspect the problem.

2. Identify the relevant diagnostic.

3. Form a possible explanation.

4. Inspect the affected code.

5. Try a targeted change.

6. Rerun relevant checks.

7. Review the result.

8. Explain the lesson learned.

The workflow must adapt to findings and failed tests. Do not force every error through a rigid sequence.

#### FR-07: Corrected code

Generate a correction proposal when sufficient information exists.

Provide:

* Proposed code or patch.

* Explanation of the changes.

* Original versus proposed code comparison.

* Relevant diagnostics.

* Validation status.

* Remaining issues.

Preserve the original source until the user explicitly accepts or copies the proposed correction.

#### FR-08: Repair limitations

Explicitly report:

* Unsupported languages or constructs.

* Missing expected behavior or tests.

* Missing dependencies.

* Failed repair attempts.

* Unresolved diagnostics.

* Checks that were not performed.

* Execution timeouts or unavailable execution environments.

* Cases in which the system cannot confidently identify a root cause.

Do not invent confidence percentages or guarantees.

#### FR-09: Verification

Where applicable:

* Re-run syntax validation.

* Re-run static analysis.

* Execute permitted tests in isolation.

* Compare test results before and after the proposed repair.

* Identify regressions.

* Report exact executed checks and their results.

A fix is verified only against the checks that actually ran.

## 22. SECURITY

Security is mandatory, particularly because the product processes and may execute untrusted source code.

### Code execution isolation

Never run arbitrary user programs in the main API process or a privileged application container.

Use a separate, appropriately isolated execution environment.

Apply:

* Execution timeouts.

* CPU and memory limits.

* Process limits.

* Bounded output.

* Restricted filesystem access.

* No application secrets in the execution environment.

* Network isolation or explicit deny-by-default network rules.

* Temporary workspace cleanup.

* Non-privileged execution identities.

* Worker lifecycle and cancellation controls.

* Limits on concurrent execution.

A normal Python subprocess or a virtual environment alone is not an adequate sandbox.

Do not claim strong isolation unless the implementation and configuration support it.

### Input and dependency security

* Validate source size and request schemas.

* Reject unsupported language values.

* Do not interpolate user-controlled strings into shell commands.

* Avoid installing arbitrary user dependencies automatically.

* Treat uploaded files and package configuration as untrusted.

* Protect against path traversal and archive extraction abuse if uploads are implemented.

* Bound test case counts and sizes.

### Web and API security

Review:

* Authentication.

* Authorization.

* IDOR.

* CSRF where applicable.

* XSS.

* SQL injection.

* SSRF.

* Command injection.

* CORS.

* Session handling.

* Rate limiting.

* Secrets exposure.

* Sensitive logs.

* Dependency vulnerabilities.

* Privilege escalation.

* Database grants and RLS.

### AI-specific security

* Treat user code and model outputs as untrusted.

* Do not let code comments or source strings override application policies.

* Never allow model output to authorize privileged operations.

* Validate any generated patch before execution.

* Limit tool access to the minimum required.

* Do not expose secrets to the model unnecessarily.

* Prevent untrusted code from reaching AI provider credentials.

* Require explicit application-level policy for operations with side effects.

### Secrets

Use environment variables or an appropriate secret manager.

Maintain a safe `.env.example` where appropriate.

Never commit actual credentials.

Do not disable security controls to make a demonstration easier.

7. Run related regression tests.

8. Inspect the resulting changes.

9. Continue with dependent tasks only when safe.

* Suppress important exceptions to create the appearance of success.

* Disable tests to pass validation.
